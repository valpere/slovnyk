# Початковий профіль сервера

Стан 2026-11-10: **пропозиція для вибору й приймання цілі**, не виміряний мінімум
і не погоджений тариф. Oracle зайнятий; його не перевіряли й не змінювали.

## Ресурси

| Ресурс | Початковий кандидат | Підстава / обмеження |
|---|---|---|
| CPU | 4 vCPU, без невідомої тривалої burst quota | DB 2 CPU + HTTP 1 CPU; решта для ОС/proxy |
| RAM | 16 GiB | DB cap 8 GiB, HTTP cap 1 GiB; запас ОС, proxy й cache |
| Дані | 200 GiB **usable** окремого filesystem | БД, artifacts, CSV, один локальний bundle, WAL/temp/reserve |
| ОС | Додатково від 20 GiB usable | ОС, images, releases, обмежені журнали; не входить у 200 GiB |
| Платформа | Linux, systemd, Docker Engine + Compose v2, NGINX | amd64/arm64: відповідна збірка та перевірка images |
| Мережа | Статична публічна адреса, TCP 80/443; SSH з обмеженим доступом | PostgreSQL і HTTP backend лише на loopback |

[Вихідний розрахунок](_assessments/2026-11-09-launch-plan/storage-budget.json):
serving payload **71.575 GiB**, сценарій restore з одним bundle — **134.384 GiB**.
Він включає припущення: WAL 2 GiB, temp 20 GiB і вільний резерв 30 GiB.
Це не верхня межа: `max_wal_size` — м’який орієнтир, `temp_file_limit` — на
процес, `work_mem` — на операцію ([PostgreSQL 17](https://www.postgresql.org/docs/17/runtime-config-resource.html)).
200 GB у тарифі — лише ~186.3 GiB; порівнювати фактичні usable bytes.

Другий повний dataset додає приблизно 71.076 GiB до WAL/temp. Такий staging
разом із наведеним restore-сценарієм перевищить 200 GiB. Перед кожним імпортом,
restore чи індексуванням перерахувати peak, retained datasets і backups;
за недостатнього запасу збільшити диск або погодити окремий cleanup.
Автоматичного видалення немає. Монітор попереджає при free <30 GiB; він не
зупиняє writers і не гарантує, що резерв не буде вичерпано між перевірками.

## Backup і канали

Власник обрав копію **до відкриття та після кожного оновлення даних**, без
щоденного розкладу й автоматичного видалення. Off-host місце — цей локальний
комп’ютер; пропонований приватний шлях `~/backups/slovnyk/`. Нинішні локальні
репетиції ще не є передаванням із cloud host. Один виміряний bundle ~10.809 GiB;
для нової копії та, за потреби, зашифрованого пакування потрібні окремі вільні
bytes понад збережені копії й локальний резерв. Повторювати preflight щоразу.

Канал аварійних сповіщень — **Telegram**. Token/chat ID ще не налаштовані;
сповіщень не надсилали. Серверний timer перевіряє readiness і диск щохвилини;
зовнішній watchdog для повного host/network outage ще потрібно визначити.
[Процедура резервування](BACKUP_RESTORE.md#політика-першого-read-only-запуску-2026-11-10),
[конфігурація й запуск](../deploy/README.md).

## Вибір провайдера

[Перевірені кандидати й ціни](SERVER_CANDIDATES.md): пропозиція netcup Lite 3,
обмеження Oracle Always Free та альтернативи. Сервер і допустимі витрати
ще не обрані; published specs не є target acceptance.

## Приймання

Для конкретного хоста зафіксувати фактичні CPU/RAM/filesystems, архітектуру,
мережу, storage performance, bandwidth/egress quota та повну місячну вартість.
Орієнтир власника ~$10/місяць не є підтвердженням доступності такого профілю.
Після вибору пройти [профіль навантаження й off-host restore <=24 h](LAUNCH_PLAN.md).
Локальні caps і syntax checks не закривають AT-16 або target RTO.
