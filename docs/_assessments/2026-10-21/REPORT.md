# Оцінювання специфікації Slovnyk через tumanomir

Дата: 2026-10-21. Оцінено вісім канонічних документів з `docs/`;
код застосунку та міграцію даних не оцінювали, бо їх ще немає.

## Висновок

Трасування після адаптації розмітки повне: **18 вимог, 0 без зв'язку,
K_drift = 0**. Незалежна структурна перевірка підтвердила наявність компонентів
HLD, посилань, use cases і відповідність таблиці трасування.

Стохастичний експеримент показав **D_pair = 0,4886**, **H_norm = 1** за п'ятьма
генераціями. Отже, цей інструмент дає різні Go-декларації для поточного пакета
документів. Це привід уточнювати контракти перед реалізацією, але не оцінка
правильності архітектури чи гарантія, що причина розкиду саме в неоднозначності.

## Детермінована перевірка

| Вхід | Вимог розпізнано | Без зв'язку | K_drift verdict | D_const |
|---|---:|---:|---|---:|
| REQUIREMENTS до адаптації | 0 | 0 | skipped | 0 |
| REQUIREMENTS після адаптації | 18 | 0 | ok | 0,03692 |
| Усі docs після адаптації | 18 | 0 | ok | 0,00730 |

Початкові ID `FR-01` не були тегами інструмента. Нульовий exit code за
`requirements=0, verdict=skipped` не означав, що вимоги пройшли перевірку.

Зміни: ID у рядках requirements оформлено як `[REQ-FR-01]` / `[REQ-NFR-01]`,
додано стрілки до вже визначених основних компонентів і стабільні anchors у HLD.
Поведінка продукту й критерії приймання не змінювалися. Отже, це виправлення
машинозчитуваного трасування, а не доведене покращення змісту специфікації.

K_drift перевіряє синтаксичний зв'язок, а не існування цілі або семантику.
Тому окремо звірено всі 18 визначень, 18 рядків TRACEABILITY, унікальні AT,
UC та FUN targets і локальні Markdown-посилання:
[trace-validation.json](trace-validation.json). Це перевірка документів,
**не** виконання запланованих приймальних тестів застосунку.

D_const — лексична щільність спеціальних маркерів; отриманий `warn` не блокує
інструмент. Не дописували маркери чи обмеження лише заради числа 0,35.

Результати: [before-requirements.json](before-requirements.json),
[before-all-docs.json](before-all-docs.json),
[after-requirements.json](after-requirements.json),
[after-all-docs.json](after-all-docs.json). Поруч `*-run.json` містять команди,
exit codes і stderr. Для обох повторних check використано `--k-drift-max 0`.

## Межі інтерпретації

PromptV1 просить лише Go-типи, константи й сигнатури з порожніми тілами;
перевірка не встановлює правильності пошуку, транзакцій, міграції або безпеки.
Поточний CLI не зберігає raw generations, тому немає підстав приписувати
конкретну різницю типів конкретному неоднозначному реченню.

N=5 — пілот, CI широкий; H_norm тут максимальна через п'ять окремих кластерів,
а не означає «100% неоднозначності». Один instrument не відокремлює шум моделі
від впливу специфікації. Cloud model tag/digest реєстрації не фіксує ваги сервера
і не доводить точне виконання sampling options провайдером.

Повний пакет змішує нормативний контракт, опис старої системи, відкриті питання
та етапи. Межі того, які саме Go-декларації генерувати, не задані як окремий
implementation contract. Before/after стохастичне порівняння не виконувалося;
покращення D_pair після додавання розмітки не стверджується.

## Практичні наступні уточнення

Це висновки читання документів і меж експерименту, а не автоматично локалізовані
tumanomir дефекти:

1. До реалізації відповідного модуля зафіксувати точні типи LookupRequest,
   LookupPage, cursor, помилки та state transitions імпорту. Зараз HLD задає
   логічний контракт, але залишає свободу Go-декларацій.
2. Перед повним імпортом визначити DDL, довгі ключі/індекси, provenance та
   формат DB export на основі реальної схеми. Частина цих рішень навмисно відкрита.
3. Закрити OQ-02 про авторитетне джерело, OQ-04 про старі URL й OQ-05 про права
   на корпус до відповідних етапів запуску. Вимірювання не може дати ці відповіді.
4. Встановити числові capacity/SLO gates після ресурсного профілю та репетиції.
5. Наступні вимірювання робити також на вузьких незмінних контрактах модулів
   з тим самим instrument. Не міняти нормативні вимоги для зниження метрики;
   поведінку перевіряти AT-тестами з TRACEABILITY.
