# Повний структурний аудит CSV

Дата: 2026-10-24. Джерело — остаточна колекція `../slovnyk1.0/csv/`.
Старі файли читалися без змін. Публікація даних не виконувалася.

## Результат

| Перевірка | Результат |
|---|---:|
| Повністю перевірені файли / gzip members | 992 / 992 |
| Напрямлені пари / вихідні коди локалей | 992 / 32 |
| Логічні CSV-записи | 56 455 068 |
| Різні чотирипольні кортежі | 56 455 068 |
| Точні дублікати / структурно відхилені записи | 0 / 0 |
| Стиснені / розпаковані bytes | 535 766 648 / 2 252 196 596 |
| Максимальні source/target поля | 223 UTF-8 bytes / 182 code points |
| Максимальний serialized record, із terminator | 390 bytes |
| Максимальний розпакований файл | 15 490 076 bytes |

Усі файли прочитані до EOF, UTF-8 коректний. Власна лексична перевірка
контролює quoted fields, doubled quotes, LF/CRLF і заборонений bare CR;
кількості звірені з `csv.reader(strict=True, newline="")`.
Окрема перевірка zlib перевірила точні межі gzip members, checksum/trailer
і відсутність сторонніх bytes, включно з нульовим padding, який Python gzip
дозволяє. Повторні SHA-256 усіх джерел збігаються з початковими.

Фактична пара кожного запису відповідає назві його файла; кожна пара
представлена одним файлом. Тому точна дедуплікація всередині файлів доводить
також відсутність однакових чотирипольних кортежів між файлами. Повторних
compressed SHA-256 немає. Непорожні коди локалей мають по 5 bytes.
Не знайдено NUL, порожніх полів, перевищення admission limits, source-полів
понад query limits або заборонених у запиті control characters.

## Особливості, які треба зберегти

- **118 009 додаткових source-написань** із тим самим нормалізованим ключем
  у межах відповідної пари: NFC → full casefold → NFC, Unicode 15.0.0.
  Це кількість додаткових форм, а не кількість груп колізій чи унікальних
  слів у всьому корпусі. Вони не є дублікатами; не зливати raw-написання.
- **20 записів у 13 файлах** мають крайні пробіли source. За чинним контрактом
  query обрізається, source — ні; exact-форма їх не адресує буквально,
  але маска та експорт зберігають доступ. Не очищати автоматично.
- **15 021 запис у 919 файлах** містить буквальні `*`/`?` у source.
  Для буквального точного пошуку потрібен наявний `mode=exact`; основна
  auto-форма трактує їх як маску. Перед UI acceptance перевірити доступність
  цього способу користувачеві, без обов’язкового перемикача для всіх пошуків.
- Пара `sr-rs → sr-rs` присутня, `en-gb → fr-fr` відсутня. Не видаляти першу
  й не генерувати другу за припущенням про повну матрицю.

**Звіту про структурні втрати для погодження зараз немає: виявлено 0.**
Це не гарантія мовної якості перекладів, історичної повноти старої БД,
відповідності майбутньому production manifest або коректності Go importer.
Таблиці provenance/ledger, round-trip exports та reconciliation digests
ще потребують реалізації й перевірки.

## Метод і відтворення

Python 3.12.3, Unicode 15.0.0, Linux x86-64; developer machine AMD Ryzen 7
7700, 16 logical CPUs, близько 61 GiB RAM. Основний аудит — 252.404 s,
peak RSS 527 236 KiB (~515 MiB); повторна SHA/gzip перевірка — 4.100 s.
Імпорт-проба SQLite працювала паралельно; це не ізольований benchmark.
Аудитор тримає один розпакований файл і його sets/maps у RAM; це діагностика,
а не потоковий production importer або перевірка пам’яті Oracle Micro.

```bash
python3 -m unittest discover -s docs/_assessments/2026-10-24-csv-audit -v
python3 docs/_assessments/2026-10-24-csv-audit/audit.py \
  ../slovnyk1.0/csv tmp/csv-audit-fresh.json
python3 docs/_assessments/2026-10-24-csv-audit/verify_snapshot.py \
  ../slovnyk1.0/csv tmp/csv-audit-fresh.json tmp/csv-snapshot-fresh.json
```

Сім синтетичних tests пройшли. Для повторення потрібні нові output paths:
інструменти відмовляються перезаписувати результати.
Докази: [result.json](result.json),
[snapshot-verification.json](snapshot-verification.json), [audit.py](audit.py),
[verify_snapshot.py](verify_snapshot.py), [test_audit.py](test_audit.py).

## Уточнення контрактів під час перевірки

У чинних документах узгоджено три вже запропоновані правила:
FR-08 використовує повний manifest fingerprint; HLD розрізняє retryable
interruption і terminal failed; DATA_MODEL не вимагає аудиту живої старої
БД для необов’язкового майбутнього DB adapter. Поведінку пошуку й дані
цими уточненнями не змінено.
