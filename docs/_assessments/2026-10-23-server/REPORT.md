# Оцінка сервера Oracle для Slovnyk

Дата: 2026-10-23. Користувач визначив локальну розробку та майбутнє
розгортання в Oracle Cloud. Наявний сервер доступний як `ssh psysoft`,
зараз зайнятий і буде звільнений. Дозволено лише read-only дослідження.

## Спостережені характеристики

| Параметр | Результат |
|---|---|
| OCI shape | `VM.Standard.E2.1.Micro`, підтверджено instance metadata |
| Архітектура | x86-64, AMD EPYC 7551 |
| Видимі CPU | 2 логічні CPU, 1 core / 2 threads; це не гарантія виділеної CPU-потужності |
| CPU за описом Oracle | Базова частка 1/8 OCPU з можливістю додаткового використання ресурсів |
| RAM | 1 GB за metadata, 954 MiB за `free`; available близько 524 MiB |
| Swap | 1 GiB, використано близько 12 MiB |
| Диск | Віртуальний block device 46.6 GiB; root ext4 близько 45 GiB, вільно близько 41 GiB |
| ОС | Ubuntu 24.04.5 LTS, kernel 6.17.0-1020-oracle |
| Поточне навантаження | Load average 0.00/0.00/0.00; коротка вибірка vmstat близько 100% idle, без активного swap I/O |
| Сервіси | Працюють Caddy, поточний застосунок та системні/OCI агенти |

`command -v` не знайшов psql/postgres, Go, Docker або Podman у PATH SSH-сесії.
Це не повна перевірка встановлених пакетів. Зупинка поточного застосунку
звільнить частину ресурсів, але не змінить ліміти shape.

Oracle metadata також повертає nominal `ocpus: 1.0`; для capacity-оцінки Micro
використано спеціальний опис shape, а не кількість CPU, видиму гостьовій ОС.
Джерело: [Oracle Always Free Resources](https://docs.oracle.com/en-us/iaas/Content/FreeTier/freetier_topic-Always_Free_Resources.htm).

## Локальні дані для оцінки масштабу

У `../slovnyk1.0/csv/` перевірено всі 992 `*.csv.gz`:

- Стиснений розмір: 535 766 648 bytes, близько 511 MiB.
- Кількість CSV-записів: **56 455 068**; це входження, а не кількість унікальних перекладів.
- Усі прочитані записи мають чотири поля; помилок gzip/UTF-8/CSV не виявлено.
- Сума ISIZE із gzip trailers: 2 252 196 596 bytes, близько 2.10 GiB;
  це довідкова оцінка, а не вимір розміру PostgreSQL. ISIZE враховує останній
  member modulo 2^32.

Підрахунок виконаний локально потоковим Python `gzip.open`, UTF-8-sig,
`newline=''`, `csv.reader(strict=True)`; 29.9 s на машині розробки.
Старі файли не змінювалися, їхній вміст не завантажувався на сервер.
Це перевірка читабельності та кількості записів, не acceptance lossless parser,
не аудит дублікатів/локалей і не доказ повноти щодо старого сервісу.

## Висновок і рекомендація

Наявний Micro — кандидат для невеликого тестового запуску або обмеженого
набору. Для основного розгортання Go + PostgreSQL з повним наявним корпусом
**не рекомендований без успішної повної репетиції та навантажувальної перевірки**.
Це інженерна оцінка ризику, не доведена неможливість запуску.

Основні обмеження — 1 GB RAM, мала базова CPU-частка та непідтверджений запас
диска. У поточній моделі, крім translations, зберігаються import_records,
origins, hashes та індекси; для наступної версії потрібні active і staging,
а також WAL, тимчасові файли й експорти. Розмір БД не дорівнює розміру CSV.
Маски передбачають scan/sort під deadline; їхня продуктивність на Micro невідома.
Пам'ять PostgreSQL для sort/hash витрачається на операції та конкурентні запити:
[PostgreSQL resource consumption](https://www.postgresql.org/docs/current/runtime-config-resource.html).

Для пошуку альтернативи пропонується початковий профіль: **2 повноцінні vCPU,
4–8 GiB RAM, 80–100 GiB block storage**. Це орієнтир для репетиції, не погоджений
мінімум чи гарантія capacity. Oracle A1/ARM також можна розглянути після перевірки
доступності в акаунті та сумісності обраних залежностей; ресурси не створювалися.

Після реалізації виміряти розмір одного/двох datasets з індексами та origins,
peak RAM, WAL/temp disk, import/verify duration і exact/prefix/infix p50/p95
при погодженій конкурентності. Подальше уточнення користувача: орієнтовний
пік старого сервісу до 10 запитів/с; це не вимір поточного трафіку. Профіль
запитів, RPO/RTO та остаточний сервер залишаються відкритими. Після цієї оцінки
користувач погодив p95 звичайного пошуку <=1 s на сервері та DB deadline 2 s
і запропонував дослідити SQLite для слабкого сервера; попередня рекомендація
стосувалася саме Go + PostgreSQL.
Сама оцінка 10 запитів/с не підтверджує придатність Micro: важливі вартість
exact/mask, конкурентність і фактичні query plans. На зайнятому сервері не запускалися benchmarks,
не встановлювалися пакети, не змінювалися конфігурація чи стан сервісів.
